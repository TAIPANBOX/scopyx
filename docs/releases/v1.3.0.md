# Scopyx 1.3.0

This is a minor release. A fetch through the TokenFuse MCP broker now carries the run that asked for it, so this plane's record joins the rest of that run. A call that names no run behaves as it did.

## Upgrade

Nothing breaks, and an existing run needs no edit. Pull `ghcr.io/taipanbox/scopyx:v1.3.0` and `ghcr.io/taipanbox/scopyx:v1.3.0-chromium` in place of the 1.2.0 tags. The configuration and the journal are the same. The image sizes in the README are the 1.0.1 measurements.

The broker names the run from TokenFuse v1.22.0, for an upstream listed in `TOKENFUSE_MCP_UPSTREAM_LABELS`. With an older broker no header arrives, and each fetch keeps the process's run. Rollback is to run the 1.2.0 image.

## Added

- **A fetch carries its run (#74).** The MCP server was handed one run when the process started, so the record said one `run_id` per process, whichever run asked. A call now names its run in `X-Fuse-Run-Id`, the header TokenFuse reads from its own callers, and the run reaches the fetch's record and the question put to the policy plane.

## Behaviour

- **A label and not an identity.** Nothing is admitted on the header, and the agent still comes from the credential alone. A caller holding a key of its own can write any run, as it can at the gateway.
- **One bounded word.** A header that is not printable ASCII with no space, within 256 bytes, falls back to the process's run and the fetch goes on, so a header cannot write anything else into the record.
- **No header, no change.** A client with no broker in front of it is labelled by the process, as it always was.

## Changed since 1.2.0

- #74, `feat(mcp): a fetch through the broker carries the run that asked for it`. Invariant 17, seven scenarios in `features/a-fetch-carries-its-run.feature`, 20000 seeded inputs against hostile headers.
- #73, `docs(readme): the stack diagram shows the optional broker route`.

No other commit lies between the 1.2.0 tag and this release.
